# C3 双流实验的内存压力与回环停滞

2026-09-23，状态：已确认并纳管 lwIP 零窗口 ACK 根因修正；资源预算和网络故障矩阵仍未完成，不能据此发布或宣称 P4 通过。

## 实验边界

独立 `examples/tcp_proxy`、ESP-IDF v6.1、ESP32-C3、官方 FRPS v0.71.0。实验服务只在本机局域网监听，代理入口只绑定本机回环；真实生产服务未修改。板上目标为两条 `127.0.0.1` TCP echo 连接。设备须先完成真实 SNTP，再完成严格 TLS、Token 登录、代理注册与首次 Pong；未调整证书校验强度或协议容量。

## 已确认现象与修正

1. 第一轮在 Wi-Fi 获取 IP 前启动 SNTP，未获得可信时间，客户端保持未启动。调整为取得 IP 并配置 DNS 后启动 SNTP，后续实板完成同步。
2. 第一轮 Wi-Fi 在线时最大连续堆块为 114688 字节，小于原单块会话的 127728 字节。先拆出 AEAD 接收区仍在严格 TLS 后分配失败；最终改为会话 41264 字节、Yamux 20912 字节、AEAD 接收区 65552 字节。合计容量不变，实板随后到达 READY。
3. 默认网络缓冲下，两连接各 1/1024 字节往返通过；各 65536 字节时接收截断，客户端报 CRYPTO_ERROR，全程最低 heap 降至 864 字节。该数据证明严重内存压力，尚未捕获对应 PSA 原始状态码，不能直接断言某一 PSA 分配是唯一根因。销毁后任务数 7、socket 数 1、最大连续块 114688 字节。
4. 将样例 Wi-Fi 静态 RX 调为 6、动态 RX/TX 各 12，TCP send/receive window 各 2880 后，READY 时 heap 47280、最大连续块 23552 字节，采样分配失败次数为零；小载荷再次通过。双路各 65536 字节时转发超时，`task_wdt` 连续报告 IDLE 得不到运行，当前任务为 `tcpip`，样例任务也不再输出周期采样。

第四轮告警寄存器映射到 `heap_caps_aligned_alloc_base`、`ip4_output_if_opt_src`、`xQueueSemaphoreTake` 和 `pbuf_free`。它们支持网络任务持续处理分配/报文的判断，不足以证明具体 ACK 循环、某个 lwIP 缺陷或协议实现无责。不可用关闭看门狗、降低校验、改换板外 echo 目标或直接增加超时作为通过依据。

## 零窗口根因与受管 SDK

后续使用只读 `LWIP_HOOK_TCP_INPACKET_PCB` 有界记录，观察到双方在 `len=0`、`ACK`、`wnd=0`、`seq=rcv_nxt` 时不断互回同一空 ACK。固定 SDK 的 `tcp_in.c` 以 `rcv_nxt + rcv_wnd - 1` 判断空报文范围，零窗口时错误拒绝了这个合法 ACK。该行为违反 [RFC 9293 Table 6](https://www.rfc-editor.org/rfc/rfc9293.html#table-6)：零长度、零窗口时应接受 `SEG.SEQ == RCV.NXT`。

最小修正只将空报文分支改为：零窗口比较 `seqno == rcv_nxt`，非零窗口保留既有范围判断。没有 ACK 限流、丢包绕路或看门狗例外。独立回归直接编译真实 lwIP，覆盖两端窗口填满/恢复、空包边界、错误序号拒绝和序号回绕；原始 `c6f2f878e7b0f86033214b85547d579be43351e3` 的两项用例均失败，修正后的两项 ASan/UBSan 用例均通过。

维护者已明确允许纳管最小 SDK 根因修正并继续验收。公开源依赖 [esp-lwip](https://github.com/darren-you/esp-lwip) 保留 Espressif 上游历史与 BSD 许可，精确修正提交为 `3dc581c9584da3b3bd6207d31e17a24bb8ef4033`。ESP-IDF 仍固定 v6.1 提交 `fff9895c82d744c7237be8847347bdd1b07c6643`，组合由本仓 `sdk-lock.json` 和 `tools/sdk.py` 唯一声明；全新公开 checkout 已准备成功。CMake 拒绝原始 lwIP、其他 SDK 修改和外部 lwIP 组件覆盖。原系统 SDK 保持未修改。

隔离修正版实板对照已完成：

- 双连接各 1、1024、65536、300001 字节逐字节往返通过。
- 100 次 destroy/create/真实 FRPS 登录及同实例 3 次 stop/start 通过；销毁后任务数 7、socket 数 1，heap 225168–227308 字节，未见持续下降。
- 3 次 station stop/start 后双流各 65536 字节恢复通过。
- 隔离 FRPS 重启后自动回到 READY，但随后双流测试有一条 EOF 截断；该项仍失败，不能用 READY 替代数据恢复。
- 全程最低 heap 4168 字节、最低采样栈余量 1196 字节、采样分配失败次数为零，未再出现 ACK 循环或看门狗。heap 仍远低于计划预算，零次分配失败不代表资源充足。

## 正式 SDK 与资源复用复测

`p4-locked-sdk-20260923` 使用从公开精确提交准备的完整 SDK，并共享单份工作握手 JSON 区。C3 会话对象从 41264 降至 33072 字节；双流 1/1024/65536/300001 字节、100 次重建、3 次同实例重启、3 次 station 周期与首次 FRPS 重启恢复通过。销毁后任务/socket 为 7/1，100 个周期的 esp_timer dump 均为 18 项；heap 225216–227292 字节，首末十次中位数 225492/227260，未见持续下降。所有采样任务栈余量至少 1196 字节。

追加 FRPS 重启后双流各 300001 字节，前三次通过，第 4 次再次截断；客户端保持 READY，`status.work.last_error = EFRP_TIMEOUT (-9)`。全程最低 heap 12432 字节，采样分配失败为零，没有再次出现 ACK 循环或看门狗。该事实说明工作握手区共享未解决全部网络故障，不能归因于已修正的零窗口空 ACK 条件。需进一步区分本地 TCP、Yamux 输出停滞和测试端先发完再读形成的背压；现阶段不调整 2.5 秒停滞期限。

本轮 15 项 ASan/UBSan 全套通过；新增部分握手与旧活动流 RST 并发场景后受影响测试通过，故意无条件清空共享区的错误变体在该场景失败。测试服务端现显式关闭已接受 TCP 连接，再等待控制读取退出，保留客户端自身 fd 基线检查；此前等待超时日志保留。客户端两项 TSan 通过。实板结束后恢复整个原应用槽，双份全量回读等于前置基线，UUID/revision 5/Wi-Fi/原 Bridge 已恢复，隔离服务已停止。

随后按生命周期复用登录握手与认证后控制区，控制发送区按真实 1024 字节输入加 AEAD 开销设置；保留 65552 字节 AEAD 接收区和 4096 字节 JSON 上限。C3 会话对象进一步降至 24848 字节，两步合计节省 16416 字节。五项受影响 ASan/UBSan 回归通过，包含控制会话、百轮双流、故障、worker 与配置；后续 MCU 结果见下节，仍不能宣称完整预算或 P4 通过。
